# Офлайн-справочник: контракт jana-address-db/1.0

База разрешения путей выпуска — каталог его `manifest.json`. База путей исходников и команд — корень репозитория. Выпуски неизменяемы; конечный manifest создаётся после всех шардов. Файл `manifest.pending.json` не является опубликованным выпуском. Корневой `artifacts/address_db/manifest.json` выбирает проверенный выпуск и дополнительные артефакты.

Вложенный блок `extraction` описывает входной архив наблюдений: его `files` разрешаются относительно `extraction.path_base`, указанной в корневом manifest. У архивных manifests v007/v008 вложенные имена файлов относятся соответственно к `artifacts/address_db/extraction-v003-canonical` и `artifacts/address_db/extraction-v004-recheck` от корня проекта; это метаданные сборки, не потребительские шарды. Унаследованные `local_file` в source_catalog относительны к `Data/` и не являются обещанием, что все перечисленные сторонние файлы прочитаны или нужны для работы.

## Чтение

`admin.json`, `geonims.json`, `house_districts.json`, `conflicts.json`, `name_index.json` — описатели коллекций: `schema_version`, `collection`, `record_count`, `shards`. Каждый шард — обычный JSON-массив UTF-8. В описателе есть относительный путь, число записей, размер и SHA-256 каждого шарда. Максимальный целевой размер — 40 миллионов байт. Формат одинаков у минимального и общереспубликанского выпуска.

Чтение стандартным Python: добавить `artifacts/address_db/tools` в путь импорта и вызвать `db_common_v1.read_collection(release_path, 'house_districts')`. Исходный JSON, PBF, osmium и shapely для чтения не требуются. Не загружать всю страну в память без необходимости. Потоковый читатель держит один шард. Для быстрых выборок по компонентам рекомендуется дополнительный SQLite.

SQLite хранит те же JSON-записи без потерь, сжатые zlib в колонке `payload`. Таблицы: `admin`, `geonims`, `houses`, `names`, `metadata`. `sqlite_reference_v1.unpack(blob)` восстанавливает запись стандартными библиотеками. Индекс `house_components` использует `(locality_id, geonim_id, house_number, corpus_block)`; неизвестный корпус сравнивается SQL-условием `IS ?`. Это индекс компонентов адреса, не таблица ответов на входные строки и не индекс клиентских id. Подтверждённые дубликаты адресных наблюдений остаются отдельными строками; запрос возвращает массив кандидатов.

## Административные записи

ID КАТО сохраняются. `names.ru/kk/source_default` — исходные имена; `display_name` — удобное отображение; `city` — имя населённого пункта без обозначения типа. `province` и `province_id` вычислены по исходной цепочке родителей; `province_rule.chain` делает правило проверяемым. Для городов республиканского значения province совпадает с именем города. Названия «область Абай», «область Жетісу», «область Ұлытау» сохраняют форму КАТО, без придумывания русских прилагательных.

`parent_id`, `parent_candidates`, `parent_link_method`, `link_status` не превращают восстановленную иерархию КАТО в выгрузку государственного адресного регистра. Родительские кандидаты, население с датой, индивидуально не подтверждённые сельские категории и статус активности сохраняются. `boundary_links` и варианты OSM — дополнительные свидетельства, а не изменение исходных названий. Явный тег КАТО OSM также проверяется по имени и региону: старый код может существовать в текущем КАТО уже у другого объекта. Отклонение отражается в `kato_tag_status`, исходный тег не исправляется.

## Геонимы и ключи

`locality_id` допускает null. `locality_link` содержит статус matched/ambiguous/unmatched, метод, кандидатов и свидетельства. `role` различает street/address_area; `type` и `type_origin` показывают тип источника. Значение highway в type — дорожный тег OSM, не автоматически русское обозначение «улица». Статус актуальности относится только к снимку.

`variants` содержит текущие варианты и язык, если он известен. `old_names` хранится отдельно. Унаследованные старые имена геонимов с `target_status=inherited_unverified` сохраняются, но не входят в исторический поиск: старый сборщик мог перенести old_name здания на его улицу. Новое старое имя улицы принимается только с самого именованного дорожного объекта; имя здания не становится именем улицы.

`name_index` отображает каждый `key` в массивы `current_ids`, `historical_ids`, `generated_latin_ids`. Коллизии не разрешаются выбором первого ID. Нормализация меняет регистр/пунктуацию и ё/е; цифры и литеры сохраняет. Удаление обозначения типа и созданная транслитерация — дополнительные ключи поиска, не новые исходные имена и не официальная латинизация. Поиск по ключам не разрешает менять написание `street_name` в ответе парсера.

OSM-группа одинаковых имён не удостоверяет единственность физической улицы. `identity_scope` указывает это ограничение. Остановки, платформы, километровые столбы и другие служебные highway-объекты не создают геонимы улиц; их явные адресные теги, если есть, обрабатываются отдельно. Несопоставленные по населённому пункту наблюдения могут объединяться в `unresolved_name_bucket_not_physical_entity`; такой ID — только поисковая группа неподтверждённых наблюдений. Нельзя использовать её как определённый геоним для вывода района.

## Дома и районы

Номер дома и корпус сохранены строками без исправлений; null остаётся null. `geonim_id` может быть null; `geonim_candidates` сохраняет неоднозначность, `address_area_ids` — дополнительные территории. Одна строка — наблюдение/объект источника, не гарантированно уникальный физический дом.

`districts` — массив свидетельств с `district_id`, методом, `origin=observed`, датой снимка и ссылкой на источник. Геометрическое свидетельство означает район выбранной точки здания. Для прежних геометрических связей точка наследуется из исходной базы. Полная строка карточки Караганды сохранена в соответствующем текстовом свидетельстве. Исторический Октябрьский район имеет отдельный признак исторического имени и статус унаследованного, повторно не подтверждённого правового источника.

Улица и территория не получают район большинства. При нескольких районах у одного точного адреса выставляется конфликт, который блокирует соседний вывод. Архивные объекты остаются в данных, но не являются соседями. `numeric_family` — ведущая целая часть только для проверенного ограниченного синтаксиса номера; исходный номер не изменяется. Списки, диапазоны и строки с лишними словами исключаются. Квартиры, подъезды и подробная геометрия отсутствуют в потребительских домовых записях.

## Вывод по соседям

Слой находится отдельно от точных наблюдений. `policy.json` фиксирует критерии до расчёта; `validation.json` содержит результаты по каждому городу, источнику, положению внутри/на краю диапазона и многозначным улицам. `families` — исходные числовые семьи с массивом районов, не готовые ответы на неизвестные номера.

Потребитель должен проверить все `runtime_preconditions`: район отсутствует во входе, один город и один геоним определены, точного дома/корпуса нет, конфликта точной записи нет, номер допустим. Группы имён с разными явными типами (например, улица и проспект) отмечены в `quality_v007.json/geonim_type_conflicts` и исключены из соседнего слоя; единственный ID такой группы не доказывает однозначность улицы. Затем нужны меньший и больший соседи той же чётности. Конфликт выбранной семьи или разные районы равноудалённых соседей означают отказ. Результат маркируется `origin=inferred`; он не подменяет исходное наблюдение. Разрешение — только из decisions для соответствующей пары город/источник. Края и edge_uniform выключены.

В проверке целиком скрывается числовая семья, включая литеры, дроби, корпуса и повторные наблюдения. Это восстановление меток базы на development-данных, не независимая оценка отсутствующих домов или реальных клиентских адресов.

Если числовая семья запрошенного номера уже известна по другим литерам/корпусам и её районы конфликтуют, потребитель также обязан отказать. Нельзя обойти такой конфликт, исключив целевую семью и взяв соседей. Полное исключение целевой семьи применяется только в измерении с искусственным скрытием меток. `neighbour_eligible` у домовой записи отражает локальные проверки номера, активности и точного конфликта; это не замена всем условиям policy.

## Полнота, источники и поставка

`address_relations`, `relation_house_evidence` и `relation_name_index` — дополнительный слой всех отношений type=associatedStreet/street/address из PBF. Имена отношений отображаются в массивы кандидатов геонимов, отдельно от первичного индекса. Участник отношения без соответствия выбранным наблюдениям явно помечен. Отношение не заменяет без проверки прямой addr:street или внешний ключ реестра: согласия, противоречия и требующие проверки кандидаты сохранены раздельно. Домовые наблюдения с противоречащим отношением улицы исключены из принятого соседнего слоя версии 2. Для его воспроизведения `neighbour_validation_v2.py` получает `--relation-evidence`; вход фиксируется хешем.

`observation_links` связывает каждое извлечённое наблюдение PBF с домами/геонимами; `unresolved` сохраняет спорные и несопоставленные теги, точку и кандидатов. `boundary_links` и `place_links` объясняют сопоставление административных границ и населённых пунктов. Эти вспомогательные файлы нужны для аудита, но не обязательны для старта парсера. Отсутствие адреса в OSM не доказывает его отсутствия в реальности.

В source_catalog сохранены даты, статусы источников и лицензия OSM: ODbL 1.0, © OpenStreetMap contributors, выгрузка Geofabrik. Условия повторного распространения остальных исходных источников отдельно не установлены. Ссылки в каталоге не означают новую сетевую выгрузку. Ключа eGov в предусмотренных переменных нет; авторизованный сбор не выполнялся.

В Docker требуется Python и выбранный JSON-выпуск либо SQLite, плюс выбранные policy/families для соседнего слоя. Windows-библиотеки из tools/vendor и wheels нужны только для воспроизведения сборки на этой машине; их нельзя использовать как Linux-библиотеки. Linux/Docker-интеграция принадлежит следующей роли и этим заданием не проверялась.

## Воспроизведение

Из корня проекта: `python AddressParser/build_address_db.py --release v009-rebuild --reuse-extraction extraction-v004-recheck`. Без `--reuse-extraction` будет новый проход локального PBF. Уже существующие каталоги версии не перезаписываются. В среде без библиотек сборки установить `build_requirements.txt`; для этой Windows/Python 3.14 имеются локальные wheels. Сами артефакты читаются без установки пакетов.
