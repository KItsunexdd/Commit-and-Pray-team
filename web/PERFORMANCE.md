# Проверка производительности

Дополнение после основных замеров: частота canvas снижена **24 → 15 кадров/с**.
После **20 секунд без ввода** цикл остановлен — **0 кадров canvas** до следующего
движения указателя, касания, нажатия клавиши, ввода или прокрутки. Часы анимации
сохраняют позицию. Счётчик `data-frame` исключён из production. Приведённые ниже
замеры CPU относятся к предыдущей версии с ограничением 24 кадра/с.
На production-сборке проверены автоматическая пауза, пробуждение при вводе,
сохранение ручной паузы после ввода и отсутствие `data-frame` в DOM и JS-сборке.

Замеры 17.10.2026 на production-сборке. Исходная версия: `fd84665`.
Для карточки и демо отдельный локальный сервер возвращает существующие тестовые
фикстуры API. В готовой сборке подмены API нет.

## Последовательные изменения

1. Удалено постоянное вращение камеры. Окно 1280×720, светлая тема, полный режим,
   10 секунд покоя: кадры MapLibre **483 → 0**, записи SVG `d` **642 → 0**,
   объём записанных путей **21 676 705 → 0 символов**. Доля времени внутри
   rAF-обработчиков **19,07% → 0,65%**, частота rAF **50,0 → 140,5 Гц**,
   длинные задачи >50 мс **0 → 0**. Это измерение работы JS-обработчиков,
   а не общий CPU процесса; частота rAF зависит от дисплея и не равна частоте
   перерисовки неподвижной карты. Тест контроллера проверяет отсутствие фонового цикла.

2. Контур и швы на обзоре страны: **8 397 → 1 404 вершины (−83,3%)**.
   Геометрия упрощается в памяти фронтенда, исходные геоданные не меняются.
   На приближении детализация возвращается; уровни кешируются. Путь округляется
   до 0,1 px без `toFixed`, повторные значения не записываются в атрибуты и стили.
   Проекция контура страны кешируется отдельно от подъёма выбранной области;
   точки для импульса и рамки повторно используют уже спроецированную линию.

3. SVG-фильтры на полноэкранных контурах: **2 → 0**. Анимации размытого
   контура: **2 → 0**. Под тонкой линией остаётся широкий полупрозрачный штрих.

4. Поиск и карточка: **2 backdrop-фильтра → 0**, радиусы **16/18 px → 0**.
   Используются плотные фоны палитры: `#f5f8f4` в светлой теме,
   `#07170e` с непрозрачностью 91%/95% в тёмной.

5. Canvas: максимальный DPR **2 → 1**, ограничение частоты **30 → 24 кадра/с**.
   При 2560×1440 и DPR 2 буфер **14 745 600 → 3 686 400 пикселей**.
   В светлой теме остался только импульс; очищается его предыдущая область.
   Замер 1280×720 за 10 секунд после пункта 1 и после пункта 5:
   очищено **264 → 2 мегапикселя**, работа rAF **0,65% → 0,44%**.
   Во время подлёта и ручного движения карта останавливает цикл эффектов.

6. При 50 шагах подъёма вызовы `setFeatureState`: первый выбор **1 020 → 50**,
   смена выбранной области **1 020 → 100**, повторный выбор той же области **0**.
   В исходной реализации был также начальный шаг с неизменившимися значениями.
   Затемнение остальных регионов задаётся выражением цвета один раз на выбор,
   с переходом 300 мс; высота выбранного региона по-прежнему меняется за 850 мс.

7. Экономичный режим теперь реагирует на интервалы всей страницы: после прогрева
   1,5 с нужны **3 последовательных окна по 1 с**, в каждом не менее 70% кадров
   длиннее 50 мс. Прежний порог стоимости canvas **8 мс** больше не используется.
   При срабатывании: **0 кадров эффектов**, DPR карты **1**, MSAA выключен.
   MSAA отключён при создании контекста во всех режимах: его нельзя переключить
   без замены WebGL-контекста. Это сохраняет карту и подлёт при снижении качества;
   внешний контур сглаживает SVG. Системное уменьшение движения и ручная пауза сохранены.
   Измеритель использует пары соседних rAF через 200 мс; намеренная пауза не
   считается пропуском кадра. Canvas ждёт следующей отрисовки таймером, не запускает
   пустые rAF на каждом обновлении монитора. В экономичном режиме отключены также
   пульсация точек и смена примеров поиска.

После семи пунктов дополнительное профилирование показало лишнюю сериализацию
невидимых штрихов при приближении. Они отсекаются за границей экрана с запасом
12 px; пересекающие экран сегменты сохраняются. Полная маска для заливки canvas
собирается после остановки камеры. При открытии карточки этот шаг дал
**45,4 → 56,7 FPS во время полёта**, объём записей SVG за 10 с
**7 207 286 → 1 371 416 символов**. Замыкание маски и разрывы штриха проверяются тестом.

## Методика

Сравниваются сохранённый `dist` исходного коммита и новая production-сборка.
Геоданные, тестовые ответы API и сценарии одинаковы. Окно обычной проверки —
1280×720. Замер длится 10 секунд, начинается после готовности карты.
Выполнено пять сценариев: покой, выбор Алматы, разбор адреса с карточкой,
смена светлой темы на тёмную, демо. Демо проходит до «5/5 · завершено».

Средняя частота rAF всего окна включает покой после полёта; она зависит от
частоты экрана и не является FPS MapLibre. Поэтому для полёта приведена также
частота только в интервале статуса наведения. Число длинных задач — задачи >50 мс
из PerformanceObserver. Это одиночные сравнительные прогоны, не статистическая
гарантия нижней границы FPS на любом устройстве.

## Обычный режим: до → после

- Покой: частота rAF **50,0 → 130,0 Гц**, p95 интервала **34,7 → 8,3 мс**,
  длинные задачи **0 → 0**. Кадры MapLibre **483 → 0**, записи SVG **642 → 0**.
- Выбор Алматы: частота rAF за 10 с **106,6 → 114,6 Гц**,
  во время полёта **25,1 → 64,9 FPS**, p95 всего окна **34,7 → 15,9 мс**,
  длинные задачи **0 → 0**. Исходная версия сама снижала качество;
  новая завершила замер в полном режиме.
- Открытие карточки из обзора страны: частота rAF **105,1 → 111,5 Гц**,
  p95 **34,8 → 16,0 мс**, длинные задачи **0 → 0**.
  Новый подлёт отдельно: **56,7 FPS**. В исходном замере карточки частота
  только полёта отдельно не записывалась.
- Смена темы при выбранном Алматы и открытой карточке: частота rAF
  **137,3 → 140,1 Гц**, p95 **7,1 → 7,1 мс**, длинные задачи **0 → 0**.
  Этот замер сделан перед дополнительным отсечением невидимых штрихов;
  в обоих случаях при смене темы не было записей SVG-путей.
- Демо: частота rAF **73,1 → 100,4 Гц**, p95 **41,7 → 17,9 мс**,
  длинные задачи **0 → 0**. В новой версии во время полётов **67,1 FPS**;
  SVG-записи **15 036 975 → 3 910 339 символов** за окно.

## CPU в покое и сборка мусора

Отдельные трассы Chrome через Lighthouse CLI, без непрерывного измерительного
rAF и без обёрток WebGL. Между двумя метками измеряется прирост thread-time
основного потока рендерера, делённый на реальное время окна. Это **CPU основного
потока страницы**, не сумма всех процессов Chrome и не GPU. Окно начинается
через 6 с после загрузки. Сеть не замедляется; геоданные локальные.

- Десктоп, без замедления: **29,26% → 4,76% CPU**. События MinorGC/MajorGC
  **17 → 0**, максимальная пауза GC **2,18 → 0 мс**, максимальная задача
  **13,07 → 3,51 мс**, задач >50 мс **0 → 0**.
- Десктоп, CPU 4×: **16,56% → 4,68% CPU**. GC **1 → 0**,
  максимальная пауза **16,01 → 0 мс**, максимальная задача **24,78 → 20,60 мс**,
  задач >50 мс **0 → 0**. Исходная версия здесь включала экономичный режим,
  новая сохранила полный режим.
- Телефон 390×844, DPR устройства 3, CPU 4×: **14,12% → менее 0,1% CPU**.
  GC **0 → 0**, задач >50 мс **0 → 0**. В новой версии два повторения дали
  0,02% и 0,05%; таймер завершил окна через 12,58 и 12,33 с вместо 10 с,
  поэтому точность до сотых здесь не считаем значимой. В обоих вариантах
  включён экономичный режим; после оптимизации в нём нет canvas-анимации.

Нулевые кадры неподвижной карты подтверждены. Буквально нулевой CPU полного
режима не достигнут: остаются декоративные эффекты. Средняя частота полётов
без замедления превысила цель 50 FPS, но это не обещание, что каждый кадр
укладывается в 20 мс. На физическом Android проверка не проводилась.

## Демо с CPU 4×: до → после

Production, автозапуск `?demo=1`, светлая тема, окно 10 секунд начиная через
6 секунд после загрузки. В окно входят подлёты, показ карточек и паузы.
Частота rAF и задачи измерены отдельным диагностическим прогоном; CPU этого
прогона не смешивается с чистым измерением покоя выше.

- Десктоп 1280×720: частота rAF **63,4 → 71,9 Гц**, во время полётов
  **9,3 → 33,9 FPS**; p95 **71,6 → 31,2 мс**. Длинные задачи **39 → 8**,
  самая долгая **246,61 → 67,51 мс**. GC **7 → 6**, максимальная пауза
  **22,77 → 9,54 мс**. Исходная версия перешла в economy, новая — в полном режиме.
- Телефон 390×844, DPR 3: частота rAF **78,2 → 97,3 Гц**, во время полётов
  **28,8 → 59,9 FPS**; p95 **38,3 → 22,8 мс**. Длинные задачи **8 → 0**,
  самая долгая **72,78 → 45,86 мс**. GC **10 → 4**, максимальная пауза
  **4,08 → 9,43 мс**: сборок меньше, но максимум не улучшился. Оба прогона
  в economy; кадров canvas **148 → 0**.

Ограничение покрытия: отдельно все пять сценариев сняты без замедления.
При CPU 4× и мобильной эмуляции сняты покой и автодемо, включающее подлёты
и карточки; отдельной трассы смены темы под замедлением нет. На десктопе
с CPU 4× ещё остаются задачи >50 мс, поэтому отсутствие задержек во всех
режимах не заявляется.

## Повторить проверку в VS Code

В терминале PowerShell из корня репозитория:

```powershell
cd C:\terriconV\web
npm test
npm run lint
npm run typecheck
npm run build
npm run preview
```

Открыть адрес из терминала (обычно `http://127.0.0.1:4173`). В DevTools →
Performance записывать по 10 секунд после готовности карты: покой, выбор Алматы,
разбор адреса, смена темы, демо. Повторить с CPU 4× и экраном 390×844.
Карточке и демо нужен запущенный API; `preview` использует настоящий API,
даже если при сборке задан `VITE_USE_MOCKS=true`.

Автоматическая защита дополнительно проверена искусственной нагрузкой:
после устойчивых пропусков кадров включается `economy`, буфер эффектов
становится 0×0, WebGL-карта сохраняется. Эти искусственные длинные задачи
не включены в замеры выше.
